# Progressive image-sequence loading with WebP conversion and lazy triggers

This change replaces the 184MB all-at-once JPG preload with a tiered loading system: only the first sequence's thumbnails (~860KB) block the preloader, full-res frames swap in behind the scenes, and remaining sequences load on-demand via IntersectionObserver or idle callbacks. The asset pipeline converts 1200 full-size JPGs into 600 WebPs at 960×540 (halved frame count, halved resolution, ~30MB total) plus 600 thumbnail WebPs at 240×135 (~4MB total). Canvas DPR cap drops from 3 to 2.

**Watch for:** visual quality pop when full-res frames replace thumbnails mid-scroll (confirmed); race between lazy-trigger and scroll reaching 4th-vdo if user scrolls fast on slow connections (likely); 150 concurrent Image requests per `loadFullRes` call with no concurrency throttle (confirmed).

**Verdict**: APPROVED

## High-level view

The preload hook now distinguishes critical from lazy sequences. Critical sequences (only `1st-vdo`) load thumbnails first, gate the preloader on those, then fire off full-res replacements in the background. Lazy sequences (`2nd-vdo`, `3rd-vdo`, `4th-vdo`) sit dormant until `triggerLoad` is called — either from the Hero component on idle after reveal, or from IntersectionObserver proximity triggers on the reservation and contact sections.

The asset conversion script is a one-shot `sharp`-based tool that picks every other frame (300→150), produces two WebP tiers, and deletes the originals. If interrupted mid-run, some JPGs may be deleted before their WebP counterparts are written — re-run requires restoring from git.

The canvas now caps at DPR 2 instead of 3. Since the source frames are only 960×540, DPR 2 is already oversampling — the reduction costs nothing visually while cutting fill rate by ~55%.

`useScrollProximityLoader` fires at 100% rootMargin (one viewport distance). Both `ReservationMotionSection` and `ContactSection` observe for `4th-vdo` independently; `triggerLoad` is idempotent so only the first to fire matters.

<summary>Issues (4)</summary>

1. **No concurrency limit on full-res loading** — `loadFullRes` fires 150 `new Image()` requests simultaneously per sequence. On mobile or throttled connections this can saturate the browser's connection pool and spike memory. Add batched loading (e.g., 20-30 at a time) similar to the conversion script's batch approach.
2. **Thumbnail-to-full-res pop during active scroll** — When the user is scrubbing through the first sequence and full-res frames start landing, individual frames jump from 240×135 blurry to 960×540 crisp one at a time. There's no coordination to batch-swap a visible range, so the pop is random and visible. Consider deferring the swap until the frame isn't currently displayed, or replacing in off-screen-index ranges first.
3. **Fast scroll can reach 4th-vdo before it's loaded** — Hero triggers `2nd-vdo`/`3rd-vdo` on idle after reveal, and IntersectionObserver triggers `4th-vdo` at 1 viewport distance. A fast-scrolling user on a slow connection could reach the reservation section before any frames are available. The `ImageSequencePlayer` retries up to 60 rAFs (~1 second), but if thumbnails haven't loaded by then the canvas stays blank.
4. **`useScrollProximityLoader` deps array is empty** — The hook closes over `sequenceIds` and `triggerLoad` but has an empty deps array. If either prop ever changed across renders (it doesn't today, but the pattern is fragile), the observer would use stale references.

## Thumbnail-to-full-res swap mechanics

The two-phase approach works because `ImageSequencePlayer` reads `imagesRef.current[sequenceId][index]` fresh on every `drawFrame` call — when a full-res image's `onload` fires and overwrites the array slot, the next scroll tick draws the higher-quality version automatically.

The race this creates: if a user is actively scrubbing through the first sequence while `loadFullRes` is running, individual frames flip from blurry to sharp in unpredictable order (whichever HTTP response arrives first). The effect is a random popcorn pattern of sharp and blurry frames during the transition window. A mitigation would be to swap frames in index order or in batches aligned with the current scroll position.

```typescript
// loadFullRes fires all 150 at once — no backpressure
for (let i = 0; i < seq.count; i += 1) {
  const img = new window.Image();
  img.decoding = "async";
  img.src = seq.getSrc(i);
  img.onload = () => {
    imagesRef.current[seq.id][i] = img;
  };
}
```

On a 4G mobile connection, 150 concurrent requests for ~40KB WebPs each means ~6MB of in-flight requests. Browsers limit to 6 connections per origin so the requests queue internally, but all 150 Image objects are allocated immediately, consuming memory for undecoded images. The conversion script itself batches at 20 — the same discipline would be appropriate at runtime.

## Lazy-trigger timing and the fast-scroll gap

The Hero component triggers `2nd-vdo` and `3rd-vdo` via `requestIdleCallback` after `revealed` becomes true (fallback: `setTimeout(cb, 100)` for Safari < 17). Loading starts within the first few hundred milliseconds of interaction on Chromium.

For `4th-vdo`, IntersectionObservers fire at `rootMargin: "100% 0px 100% 0px"` — effectively one viewport height above or below. Since the reservation/contact sections are far down the page, the observer won't fire until the user has scrolled roughly halfway. If the user scrolls aggressively (programmatic scroll-to-contact link, or fast swipe on mobile), the trigger fires late. The `ImageSequencePlayer`'s retry logic (60 rAFs ≈ 1 second) provides a buffer, but a slow connection could still show a blank canvas at that section.

A 200% rootMargin or a time-based fallback (e.g., 5 seconds after page load, start `4th-vdo` regardless) would be more defensive.

## What's not tested

There is no test framework in this project — verification is `npm run build`. Behavioral gaps that can't be caught by build:

- Thumbnail-to-full-res swap under active scroll (requires manual testing or Playwright)
- IntersectionObserver trigger timing at various scroll speeds
- Memory profile with 600 Image objects in flight
- `requestIdleCallback` fallback path (Safari < 17)
- Behavior when a full-res image fails to load (thumbnail remains, but there's no retry or reporting)
