# Priority-based preloading for image sequences

This change splits the 1,200-frame preload (4 sequences × 300 frames ≈ 184 MB) into two tiers. The first three sequences (1st-vdo through 3rd-vdo) are marked critical and block the preloader as before; the fourth (4th-vdo) is marked lazy and downloads in the background after the preloader dismisses. The `MAX_CANVAS_DPR` cap drops from 3 to 2, reducing GPU memory on mobile. Net effect: preloader blocking shrinks from ~184 MB to ~138 MB (900 frames), and the remaining 300 frames stream in invisibly while the user scrolls.

Watch for: the 60-frame retry cap in `ImageSequencePlayer` can still expire before lazy frames arrive on very slow connections (confirmed); no bandwidth throttling or concurrency control on the lazy batch (confirmed).

**Verdict**: APPROVED

## High-level view

The preload hook now partitions its input into critical and lazy buckets. Critical sequences drive the progress bar and gate `ready`; lazy sequences start loading the instant critical ones settle. This is a straightforward two-phase approach — no IntersectionObserver, no scroll-proximity triggering — so the lazy batch still starts immediately after the gate lifts, just without blocking the UI.

The consumer-side change is minimal: one ternary in `HomeExperience` assigns priority per folder. All three critical sequences are used in the Hero scroll section and must be ready before the first scrub.

The DPR cap reduction from 3 to 2 trades marginal sharpness on high-DPI desktop displays for significant memory savings on mobile — roughly halving backing-store allocation on a 3× device.

<details>
<summary>Issues (3)</summary>

1. **Retry cap exhaustion on slow connections** — `ImageSequencePlayer`'s `arrayRetriesRef` gives up after 60 rAF retries (~1 s). If the user scrolls to `ReservationMotionSection` or `ContactSection` before the lazy `Image()` objects are created by `startLazyLoading`, the canvas stays blank permanently. Increase the retry budget or replace it with a listener on `imagesRef` population.
2. **No concurrency control on lazy batch** — `loadSequence` sets `img.src` for all 300 lazy frames simultaneously. On constrained connections this can saturate bandwidth and compete with other page resources (fonts, gallery images). Consider batching in chunks of 10–20.
3. **No error visibility for lazy failures** — Lazy frames that fail to load are silently swallowed (no `onSettle` callback is passed). Unlike critical sequences where errors still count toward progress, lazy errors are invisible. If many frames fail, the user sees blank canvas regions with no diagnostic path.

## Retry budget vs. lazy loading race

`ImageSequencePlayer.draw()` handles a missing frame (`!img`) by retrying up to 60 times via `requestAnimationFrame`, covering the brief window between `ready=true` and `loadSequence` populating the lazy array.

The pre-initialization block sets `imagesRef.current["4th-vdo"] = []` synchronously, while `startLazyLoading` is called in the same tick as `setReady(true)` but inside an async settle callback. Because `loadSequence` runs before React processes the state update and re-renders downstream components, by the time scroll triggers activate, the `Image` objects already exist in the array (just not loaded yet) and the player's second branch (`!img.complete`) handles them with a one-time load listener.

The fragile edge: if a future refactoring introduces any async boundary between `setReady` and `startLazyLoading`, or React's batching behavior changes, a component could mount and exhaust 60 retries against the empty pre-initialized array before `loadSequence` populates it. At that point the canvas goes permanently blank with no recovery path. The current code is safe by coincidence of synchronous scheduling, not by contract.

## Concurrency and bandwidth impact

The lazy batch fires 300 `img.src` assignments synchronously. Browsers cap concurrent connections per origin (6 for HTTP/1.1, more for HTTP/2), but the request queue still fills with 300 pending fetches that compete with gallery images from `ZoomParallax`, font files, and analytics requests on constrained connections. No `fetchpriority` hints or chunking strategy mitigates this. A follow-up could stagger lazy frames via `requestIdleCallback` or batch in groups of 10–20.

## Silent lazy failures

`loadSequence` is called for lazy sequences without an `onSettle` callback:

```ts
const startLazyLoading = () => {
  lazySequences.forEach((seq) => {
    loadSequence(seq); // no onSettle
  });
};
```

If frames fail to load (CDN timeout, 404, network drop), no counter increments, no error state is surfaced, and no retry is attempted. The `ImageSequencePlayer` will wait indefinitely on the `img.onload` listener that never fires (it only listens for `load`, not `error`). The result is a permanently blank frame at whatever scroll position maps to the failed image.
